# 백엔드 요청 백로그

프론트 ↔ 백엔드 사이의 미해결 항목을 한 곳에 모아 **계속 관리하는** 문서입니다.
항목 번호는 한 번 붙으면 바뀌지 않습니다 — 백엔드 회신이 번호로 참조하기 때문에
재정렬해도 번호는 그대로 둡니다.

- API 레퍼런스: [backend-api.md](backend-api.md)
- 기준 스펙: `GET /v3/api-docs` (OpenAPI 3.1.0, `info.version` = `v0`)
- Swagger: <https://antiaging-dna.anzaanza.cloud/swagger-ui/index.html>

## 화면별 API 커버리지

화면 하나하나가 무엇을 그리고 있고 그게 지금 API로 되는지를 훑은 표입니다.
**표의 ❌·⚠️가 아래 항목들의 출처입니다** — 개별 항목만 보면 "이건 왜 필요한가"가
안 보여서 같이 둡니다.

**열이 두 개인 이유가 이 표의 핵심입니다.** `API`는 *서버가 줄 수 있나*이고
`화면`은 *우리가 실제로 붙였나*입니다. 둘은 다릅니다 — 2026-08-17 점검에서
`API ✅ / 화면 ❌`인 줄이 여섯 개 나왔고, 예전처럼 한 열로만 적혀 있을 때는
전부 초록색으로 보여서 **아무도 남은 일로 세지 않고 있었습니다.** 백엔드가
막고 있는 것만 추적하고 우리 쪽 미연동은 추적하지 않은 게 원인이라,
`API ✅ / 화면 ❌`는 앞으로 **프론트의 남은 일** 목록입니다 (아래 "프론트 연동

### 10. 홈 상단 지표 카드 3개

**🔴 열림** · 다음: 백엔드 (값은 붙었고 **뱃지 규칙만** 남았습니다)

홈에 **수면 6.4시간 / 수분 1.6L / 스트레스 72%** 카드가 있고, 각각
조금 부족·좋아요·높음 같은 등급 뱃지가 붙습니다.

그런데 일지는 값을 **구간(enum)으로만** 저장합니다. `waterIntake`는 "3~5잔"이지
1.6L이 아니고, `stressLevel`은 1~10이지 72%가 아닙니다.

**요청**: 이 세 숫자와 등급을 내려주는 엔드포인트가 필요합니다. 프론트가 enum을
임의로 리터·퍼센트로 환산하면 백엔드 점수 로직과 어긋납니다.

일지의 **일간 컨디션 요약** 카드도 같은 문제입니다 — `수면 7.1h`(이건
`sleepMinutes`로 가능) 옆에 **`수분 3컵`**, `스트레스 6/10`, `기분 좋음`이 함께
나옵니다. "3컵"은 `waterIntake`의 `THREE_TO_FIVE` 구간에서 나올 수 없는 숫자입니다.
같은 엔드포인트로 묶어주셔도 좋습니다.

### 31. 점수를 **조회만 해도** 그 날짜의 점수 행이 생깁니다

**🔴 열림** · 다음: 백엔드

`GET /api/scores/{date}`가 읽기 전용이 아닙니다. 한 번도 손대지 않은 날짜를
조회하면 **그 날짜의 점수 행이 서버에 영구히 만들어집니다.**

2026-08-17 확인 (계정 `fetest01`, 2024년 6월은 이 계정이 존재하지도 않던 시기):

```
GET /api/scores?from=2024-06-01&to=2024-06-30   →  []      (2회 연속, 그대로 빈 배열)
GET /api/scores/2024-06-15                      →  200  displayTotal 83.67  grade GOOD
GET /api/scores?from=2024-06-01&to=2024-06-30   →  ["2024-06-15"]           ← 생겼습니다
   (재로그인 후에도 그대로 — 캐시가 아니라 DB에 저장된 행입니다)
DELETE /api/scores/2024-06-15                   →  405     (지울 방법이 없습니다)
```

**구간 조회(`?from&to`)는 행을 만들지 않습니다** — 위에서 두 번 연속 호출해도
빈 배열이었습니다. 부작용은 **단일 날짜 조회에만** 있습니다.

**왜 급한가**: 캘린더가 한 달을 그리려면 날짜별 점수가 필요합니다. 단일 조회를
30번 돌면 **그 사용자의 8월이 통째로 "기록이 있는 달"이 됩니다.** 홈이
`/api/scores/today`를 부르는 것만으로도 오늘 행이 생깁니다. 되돌릴 수단도
없어서, 한 번 오염되면 그 계정의 통계(월 평균·최고·연속 기록일)가 영구히
어긋납니다.

**요청**: 조회는 조회만 하도록 고쳐주세요. baseline 값을 계산해서 응답에 넣는
것과, 그 값을 저장하는 것은 분리될 수 있어 보입니다. 그때까지 프론트는 단일
날짜 조회를 **쓰지 않고** 구간 조회만 쓰겠습니다.

> **참고 — 32번과 얽혀 있습니다.** 이렇게 생긴 행은 `dailyTotal`이 `null`인
> 채로 `displayTotal`·`grade`만 채워져 있습니다. 즉 32번의 "빈 날에도 GOOD"이
> 구간 조회 결과에까지 섞여 들어옵니다.
>
> 그리고 이전에 저희가 "일지를 지웠는데 점수 행이 남는다"고 볼 뻔했던 건
> **아마 이 현상이 원인**입니다 — 삭제 누락이 아니라, 저희가 확인하느라
> 그 날짜를 단일 조회한 적이 있어서 행이 생긴 것으로 보입니다. 별도 항목으로
> 올리지 않고 여기에 묶어둡니다.

### 32. 기록이 없는 날도 점수와 `grade`가 나옵니다

**🔴 열림** · 다음: 백엔드 (22번 경계값 자체는 닫힘, 이건 적용 대상 문제)

`GET /api/scores/*`가 일지가 없는 날에도 200으로 응답하고, `grade`가 `GOOD`
입니다. 23번에서 "기록 없는 날은 404"로 정리된 건 **일지** 쪽이고, 점수 쪽은
규칙이 다릅니다.

2026-08-17 확인:

| 날짜 | `GET /api/diaries/{d}` | `dailyTotal` | `displayTotal` | `grade` |
|---|---|---|---|---|
| 2026-01-05 (가입 전) | 404 | `null` | 83.67 | `GOOD` |
| 2026-08-01 | 404 | `null` | 83.67 | `GOOD` |
| 2026-08-17 (오늘, 미기록) | 404 | `null` | 85.93 | `GOOD` |
| 2026-08-16 (전 항목 기록) | 200 | 84.83 | 85.93 | `GOOD` |

일지가 하나도 없는 **신규 계정**도 `displayTotal 83.67 / grade GOOD /
scoringVersion "v1.0-coldstart"`가 나옵니다. 가입 시 초기 진단에서 나온
baseline으로 보입니다.

**확인이 필요한 것 둘**:

1. **`grade`는 무엇의 등급인가요?** 지금은 `displayTotal`(baseline 포함)을
   따르는 것으로 보입니다. 그렇다면 22번에서 정한 3단계는 **"그날의 컨디션"이
   아니라 "그 사용자의 현재 수준"**을 뜻하게 됩니다. 캘린더 날짜 셀·지난 기록
   이모티콘은 전자를 그리는 자리라 `grade`를 그대로 쓸 수 없습니다.
2. **한 번도 기록하지 않은 사용자에게 오브가 "83점"이라고 말해도 되나요?**
   홈 오브 카드는 `displayTotal`을 그립니다. 진단 기반 출발점이라는 뜻이라면
   그렇게 읽히는 문구가 필요합니다(25번과 같은 성격).

**더 확실한 증거 — 실제 기록이 있는 날에도 `grade`가 그날과 반대로 나옵니다.**
화면 확인용으로 12일치를 채워 넣고(좋은 날·보통 날·나쁜 날을 섞어서) 구간
조회한 결과입니다:

```
2026-08-09  dailyTotal 16.32   display 77.14   grade GOOD    ← 최악의 날인데 GOOD
2026-08-10  dailyTotal 13.74   display 71.54   grade GOOD    ← 최악의 날인데 GOOD
2026-08-13  dailyTotal 94.73   display 69.39   grade WARN    ← 최고의 날인데 WARN
2026-08-15  dailyTotal 16.32   display 60.61   grade WARN
2026-08-17  dailyTotal 92.15   display 72.18   grade GOOD
```

`grade`가 `displayTotal`(누적·평활된 값)을 따르기 때문에, **그날 컨디션이
바닥인 날이 `GOOD`으로, 최고인 날이 `WARN`으로 나옵니다.** 캘린더 날짜 색과
지난 기록 이모티콘에 `grade`를 그대로 쓰면 사용자가 보는 색이 그날의 기록과
정반대가 되는 날이 생깁니다.

**프론트 우회**: 당분간 `dailyTotal === null`을 "그날 기록 없음"으로 읽고,
날짜별 등급은 `dailyTotal`에 22번 경계값(70/40)을 직접 적용하겠습니다. 이게
의도와 맞는지만 확인해주세요. — 즉 지금 저희는 `grade` 필드를 **쓰지 않고**
있습니다. 22번에서 배포해주신 필드를 안 쓰게 된 이유가 이것입니다.

### 33. `emotion`·`environment` 영역 점수가 항상 `null`입니다

**🔴 열림** · 다음: 백엔드

**요청**: 세 가지를 알려주세요.

이 셋이 정해지기 전까지 홈의 5개 영역 카드는 붙이지 않고 Figma 값으로 두겠습니다.

### 25. 홈 오브 카드 — 상태 라벨·문구·오브 상태

> **백엔드 메모 (2026-08-17)**: 22번(점수→등급 경계값)이 먼저 풀려야 합니다 —

> **백엔드 메모 2 (2026-08-17, 배포 완료)**: 22번 3단계(`grade`: 좋음/주의/위험,
> 70/40 경계값)는 배포됐습니다 — 색상을 3단계까지만 쓰신다면 지금 바로 쓸 수
> 있습니다. **7단계 세분화는 아직 미정**입니다 — 3단계 안에서 색을 더 나누는
> 기준(예: 좋음 안에서도 70~84/85~100 을 다른 색으로 볼지)이 근거 없이는

> - `GET /api/scores?from&to` 각 행의 필드: `date` · `areas` · `dailyTotal` ·

> `GOOD_*`면 `grade`는 항상 `GOOD`입니다). 색 자체를 무엇으로 매핑할지는
> 프론트에서 정해주시면 됩니다. **상태 칩·설명 문장은 여전히 27번(문장 생성

### 28. 파생값을 누가 계산하나

**🟡 프론트** · 다음: 프론트 (전부 풀림)

원본은 있는데 화면이 쓰는 건 가공값인 것들입니다. 클라이언트가 계산해도 되는지,

|---|---|---|
| `어제보다 +4` | 홈 오브 카드 | 가능 (`?from&to` 이틀) — 다만 "어제 기록이 없으면?"이 미정 |

| 지난 기록 얼굴 이모티콘 | 일지/메인 | 22번 경계값이 있어야 가능 |

**요청**: 연속 기록일만은 서버가 내려주는 편이 낫다고 봅니다(전 기간을 훑어야
해서). 나머지는 "프론트가 계산해도 된다"고 확인만 주시면 그대로 진행하겠습니다.

> **백엔드 메모 (2026-08-17)**: 제안하신 대로 갔습니다.
> - **연속 기록일**: 구현했습니다 — `GET /api/auth/me`(및 `/api/auth/signup`,

>   추가됐습니다. 정의: 오늘 날짜부터 거슬러 연속 기록 일수. **오늘치를 아직
>   안 썼어도 스트릭이 끊긴 게 아닙니다** — 하루가 아직 안 끝났다고 보고
>   어제까지 이어져 있으면 그 값을 그대로 셉니다(예: 어제까지 5일 연속이고

> - **`어제보다 +4`**: 원본으로 계산하셔도 됩니다 — `?from&to` 이틀 조회로
>   맞습니다. "어제 기록이 없으면?"은 `GET /api/scores?from&to`가 기록 없는

### 7. `stressLevel` 최솟값이 1인데 슬라이더는 0부터

**🔴 열림** · 다음: 백엔드 (0 허용이 배포되지 않았음)

`DiaryRequest.stressLevel`은 `1..10`인데 일지 화면 슬라이더는 **0~10**입니다.
0을 보내면 검증 실패합니다.

**요청**: 0을 허용해주시거나, 슬라이더를 1~10으로 바꿔야 한다고 알려주세요.

> 참고: 프론트에는 별도로 "슬라이더가 0과 미응답을 구분 못 한다"는 미해결 이슈가
> 있습니다. `stressLevel`이 optional이니 **미응답이면 필드를 아예 안 보내는** 것으로
> 처리하려고 합니다. 이 해석이 맞는지 확인 부탁드립니다.

> **백엔드 메모 (2026-08-16)**: 아직 결정 못 했습니다 — 단순 검증 문제가 아니라
> 채점식과 얽혀 있습니다. 현재 점수식(`s = 100 × (10 − x) / 9`)의 분모 9는 도메인
> `[1,10]`에 맞춘 값이라, 0을 그냥 허용하면 0과 1이 둘 다 만점으로 나와 버려서
> 11단계를 쓰는 의미가 없어집니다. 0을 정말 넣으려면 분모를 10으로 바꿔야 하는데
> 그러면 1~10의 기존 점수도 전부 바뀝니다(재보정 필요). 내부 문서
> (`docs/PLANNING_OPEN_ITEMS.md` A-6)에 옵션 두 개를 올려뒀고 기획 확인 후
> 회신하겠습니다. **미응답 시 필드 생략** 해석은 맞습니다 — 그대로 쓰시면 됩니다.

> **프론트 확인 (2026-08-17) — 0 허용이 서버에 반영돼 있지 않습니다.**
>
> - `PUT /api/diaries/{date}` 에 `stressLevel: 0` → **400 입력값 오류**,
>   `errors.stressLevel` = `"must be greater than or equal to 1"`
> - `GET /v3/api-docs` → `DiaryRequest.stressLevel` 은 `{"minimum": 1,
>   "maximum": 10}` 그대로입니다
> - 같은 계정 12일치 `dailyTotal` 이 회신 전과 완전히 동일합니다 — 분모 재보정
>   소급 재계산도 돌지 않은 것으로 보입니다
>
> 그래서 프론트는 **0을 생략하는 기존 동작을 유지**합니다. 배포가 실제로 나가면
> 알려주세요 — 슬라이더 값을 그대로 보내도록 바꾸는 건 한 줄입니다.
>
> 다만 그때 **하나가 새로 열립니다**: 슬라이더가 0에서 시작하기 때문에, 0이
> 유효한 답이 되는 순간 **한 번도 건드리지 않은 슬라이더와 "스트레스 0"을
> 구분할 수 없습니다.** 지금은 0을 생략해서 우연히 맞아떨어지지만, 0을 보내기
> 시작하면 손대지 않은 항목이 "스트레스가 전혀 없음"으로 기록됩니다. 30번과 같은
> 성격의 디자인 문제라 같이 봐주셔야 할 것 같습니다.

> **백엔드 메모 2 (2026-08-17, 배포 완료)**: 0을 허용하는 쪽으로 정했습니다.
> 슬라이더를 그대로 0~10으로 두시고 값을 그대로 보내시면 됩니다(생략 시 결측
> 처리는 기존과 동일). 채점식 분모도 9→10으로 다시 맞췄습니다
> (`s = 100 × (10 − x) / 10`, 도메인 `[0,10]`) — 기존 1~10 점수도 새 공식으로
> 다시 계산되어 화면에 소급 반영됩니다. 참고로만 알려드리면, 내부 워크드 예시

### 19. 아이디·비밀번호·닉네임의 검증 규칙

지금 상태로는 프론트가 클라이언트 검증을 붙일 수 없습니다. 서버 규칙을 모르는 채

| 항목 | 알려주실 것 |

| 아이디 | 허용 문자, 최소·최대 길이, 대소문자 구분, 예약어 여부 |

> **백엔드 메모 2 (2026-08-17, 배포 완료)**: 닉네임 규칙을 업계 흔한 잠정값으로

### 29. 취침·기상 시각을 입력할 방법이 없음

**🟣 기획** · 다음: 기획·디자인

일지 저장을 붙이면서(2026-08-17) 드러난 구멍입니다. `DiaryRequest`에는
`sleepStartedAt` / `sleepEndedAt`(`"HH:mm"`, 5번에서 확정)이 있고 서버는
`sleepMinutes`를 여기서 파생시키는데, **화면이 그 값을 받을 수단이 없습니다.**

- Figma의 `InputTime_Card`(`오전 01:30 → 오전 07:40`)는 **표시 전용 도형**이고,
  시간 피커가 디자인에 없습니다. 코드도 같은 상태입니다.
- 그래서 저장 payload에서 두 필드를 **생략**하고 있습니다. 화면에 보이는
  `오전 01:30`은 Figma 목업 값이라 그대로 보내면 없는 사실을 기록하게 됩니다.
- 결과적으로 `sleepMinutes`가 항상 `null`이고, **홈의 `수면 6.4시간` 카드는
  데이터를 붙여도 채울 수 없습니다.**

필요한 결정은 "시각을 어떻게 입력받을 것인가"입니다 — 네이티브 시간 피커,
직접 입력, 또는 수면 시간을 구간 알약으로 바꾸기. 앞의 둘은 Figma에 없는
컴포넌트라 디자인이 먼저 나와야 하고, 셋째는 API 변경까지 필요합니다.

### 30. 이미 기록한 날 다시 들어가면 '수정'이 됩니다

**🟣 기획** · 다음: 기획·디자인

열리고 그대로 다시 누를 수 있습니다. 확인이 필요한 것:

- 재진입 시 헤더·안내 문구가 그대로여야 하는지 (지금은 `항목별로 오늘의 기록을

### 26. 지표 단위가 화면과 API에서 다름

**✅ 닫힘** · 반영 2026-08-17

같은 지표를 화면과 API가 다른 단위로 다룹니다. 프론트가 임의로 환산하면 서버 값과
어긋나기 때문에 손대지 않고 있습니다.

| 지표 | 화면 | API |
|---|---|---|
| 수분 | 홈 `1.6L`, 일간 요약 `3컵` | `waterIntake` = `UNDER_2`/`THREE_TO_FIVE`/`SIX_TO_SEVEN`/`EIGHT_OR_MORE` (컵 **구간**) |
| 스트레스 | 홈 `72%` | `stressLevel` = 1~10 정수 |
| 수면 | 홈 `6.4시간`, 일간 요약 `7.1h` | `sleepMinutes` (분) — 이건 환산 가능 |

수분은 **화면끼리도 단위가 다릅니다**(리터 vs 컵). 구간 enum에서는 어느 쪽도
나오지 않습니다.

**요청**: 두 가지 중 하나로 정해주세요 — (A) 화면 표기를 API에 맞춰 구간 문구로
바꾼다(디자인 변경), (B) 서버가 표시용 값을 같이 내려준다. 스트레스 `%`도
`stressLevel`에서 어떤 식으로 환산하는지가 정해져야 합니다.

> **백엔드 메모 (2026-08-17)**: **수분은 (A)로 결정합니다** — 화면을 API 구간
> 문구(`3~5잔` 등)에 맞춰주세요. 이유: "컵 1개 = 몇 mL"라는 환산 계수는 저희
> 데이터 어디에도 근거가 없습니다. 지어낸 계수로 리터 값을 만들면 이 프로젝트가
> 처음부터 지켜온 원칙("근거 없는 anchor 값을 지어내지 않는다" — `docs/PLANNING_OPEN_ITEMS.md`
> A-3/A-4 등에서 이미 반복 적용됨)을 어기는 겁니다. 화면끼리 단위가 다른 것(리터
> vs 컵)도 이 결정으로 자연히 같은 구간 문구로 통일됩니다.
>
> **스트레스는 아직 결정 못 했습니다** — 수분과 성격이 다릅니다. 여기는 지어낼
> 계수가 필요한 게 아니라, 이미 **두 가지 서로 다른 정당한 해석**이 코드에
> 공존합니다: (1) `stressLevel` 원시값을 그대로 선형 환산 `(x−1)/9×100` — 값이

> 어느 쪽을 의도한 건지는 저희가 코드만 보고 판단할 수 없어서(둘 다 나름의
> 근거가 있는 해석입니다), Figma 쪽에 "72%가 스트레스가 높다는 뜻인지 낮다는
> 뜻인지"만 확인해주시면 그 자리에서 결정하겠습니다.

>
> **스트레스 `72%`는 "높다"는 뜻입니다 — 해석 (1)이 맞습니다.** Figma에서

### 4. 에러 응답 규격

**✅ 닫힘** · 다음: —

- RFC 9457 `application/problem+json`으로 통일돼 있습니다. 공통 필드: `type`,
  `title`, `status`, `detail`, `instance`. 검증 실패에는 `errors: { "필드명":
  "메시지" }`가 추가로 붙습니다.
- 상태 코드:
  - 로그인 실패(아이디 없음/비밀번호 틀림 — 구분해서 알려주지 않습니다) → **401**
  - 아이디 중복 가입 → **409** (`title: "아이디 중복"`)
  - 이메일 중복 가입 → **409** (`title: "이메일 중복"`)
  - 요청 값 검증 실패(필드별 `errors` 포함) → **400**
  - 가입 조건 미충족(만 14세 미만 등) → **400**
  - 일지/초기 진단 없음 → **404**

### 5. `sleepStartedAt` / `sleepEndedAt` 포맷

**✅ 닫힘** · 다음: —

- `"HH:mm"` 또는 `"HH:mm:ss"`(날짜 없는 시각). 예: `"23:30"`.
- 자정 넘김은 서버가 자동 처리합니다 — 기상 시각이 취침 시각보다 이르거나 같으면
  자정을 넘긴 것으로 보고 계산합니다. 별도 플래그나 날짜 필드는 필요 없습니다.
- 응답의 `sleepMinutes`는 말씀하신 대로 서버가 계산해서 내려줍니다.

### 6. 민감도 3종: 0~10 슬라이더 vs 4단계 enum

**✅ 닫힘** · 다음: —

- 4단계 enum(`NONE`/`SLIGHT`/`MODERATE`/`HIGH`)이 맞습니다. 기획이 이미 "슬라이더
  제거, 4점 척도로 통일"로 확정한 사안이라 목업의 0~10 슬라이더 쪽이 구버전입니다.
  화면을 4지선다(전혀 아님/약간/보통/매우)로 바꿔주세요.

### 16. 스펙 메타데이터

**✅ 닫힘** · 다음: —

- `info.title`("AntiAgingDNA API")/`version`(`v0`) 채웠습니다.
- 전 오퍼레이션에 `summary`/`description` 추가했습니다 — `/v3/api-docs`에서
  바로 확인 가능합니다.
- `content-type`이 `*/*`로 나오는 건 아직 남아 있습니다(급하지 않은 항목이라
  이번 라운드엔 안 건드렸습니다).

### 18. 가입 화면에 아이디 입력란이 없음

**✅ 닫힘** · 다음: —

- **B안**(아이디 칸 추가, 이메일 유지)으로 갑니다. `SignUpRequest`에 `loginId`가
  추가됐고 `email`은 계속 필수입니다 — 비밀번호 찾기 등 복구 수단으로 씁니다.
  STEP 1에 아이디 입력 칸을 추가해주세요.

### 20. 만 14세 확인을 누가 하나 — `birthYear`에 상한이 없음

**✅ 닫힘** · 다음: —

- 서버가 이미 검증합니다 — `가입 시점 연도 − birthYear < 14`면 400(가입 조건
  미충족)으로 거부합니다(연 나이 기준). 이 검증은 매년 바뀌는 동적 계산이라 스펙의
  `maximum` 고정 숫자로는 안 보이고, 대신 스펙 `description`에 설명을 추가했습니다.
- 체크박스(`AGE_OVER_14`)와 `birthYear` 둘 다 서버가 봅니다 — 체크박스가
  무의미한 게 아니라 이중 확인입니다.

### 21. 가입 직후 바로 로그인 상태인지

**✅ 닫힘** · 다음: —

- 확정된 설계 맞습니다. 별도 이메일 인증·본인확인 절차는 없고, 가입 성공(201)
  응답에 토큰이 바로 포함됩니다. 추가할 계획도 현재 없습니다 — 바뀌면 미리
  알려드리겠습니다.

### 23. 기록이 없는 날은 어떻게 응답하나

**✅ 닫힘** · 다음: —

- `GET /api/diaries/{date}`에 기록이 없으면 **404**입니다(200+빈 값 아님).
- `GET /api/scores?from&to`, `GET /api/diaries?from&to`는 **기록 없는 날을
  채우지 않습니다** — 있는 날짜만 배열에 옵니다. 캘린더의 "안 쓴 날"은 요청한
  구간과 응답 배열을 대조해서 판단해주세요.
- 항목 단위 미응답 해석(`conditionLevel` 제외 전부 optional, null = 미응답)도
  맞습니다.
