# 백엔드 요청 백로그

프론트 ↔ 백엔드 사이의 미해결 항목을 한 곳에 모아 **계속 관리하는** 문서입니다.
항목 번호는 한 번 붙으면 바뀌지 않습니다 — 백엔드 회신이 번호로 참조하기 때문에
재정렬해도 번호는 그대로 둡니다.

- API 레퍼런스: [backend-api.md](backend-api.md)
- 기준 스펙: `GET /v3/api-docs` (OpenAPI 3.1.0, `info.version` = `v0`)
- Swagger: <https://antiaging-dna.anzaanza.cloud/swagger-ui/index.html>
- 최초 작성 2026-08-16 · 백엔드 1차·2차 회신 2026-08-16 · 백엔드 3차 회신 2026-08-17
  · 백엔드 4차 회신 2026-08-17 (**배포 완료**) · 백엔드 5차 회신 2026-08-17 (**배포 완료**)
- 2026-08-16 화면별 전수 대조 — 25~28번이 여기서 나왔습니다

> **백엔드 4차 회신 (2026-08-17) — 배포 완료**: 3차 때 열려 있던 것 중 두 개가
> 정해져서 **운영에 반영**됐습니다.
>
> - **22번 점수→등급 경계값 결정·배포**: 종합점수·영역점수 공통 3단계 —
>   **70점 이상 좋음 · 40~69 주의 · 40 미만 위험**. `GET /api/scores/*` 의
>   `grade` 필드(`"GOOD"|"WARN"|"DANGER"`), `AreaScoreResponse` 의 `grades`
>   (영역별 5종), `GET /api/dna` 의 `baseline.grades` 로 지금 바로 조회
>   가능합니다. 이걸로 **10번(홈 지표 카드 등급 뱃지)이 사실상 풀립니다** —
>   수분·스트레스는 26번에서 이미 정해진 대로 프론트가 계산하고, 등급만
>   `grade` 필드를 쓰시면 됩니다. **25번(오브 7색)은 3단계로는 부족합니다** —
>   Figma 의 7단계 색을 이 3단계 위에서 어떻게 세분화할지는 별도로 정해야
>   합니다.
> - **17번 개발용 시드 계정 결정·배포**: 운영 DB에 바로 심는 쪽으로
>   정했습니다(가입자가 아직 없는 단계라 실사용자 데이터와 섞일 위험이
>   없다고 판단). 계정 `demo` / 비밀번호 `Demo1234` 로 로그인하면 최근
>   14일치 일지·점수가 이미 들어있습니다 — 지금 바로 화면 확인에 쓰실 수
>   있습니다.
> - **26번 스트레스 방향** — 보내주신 Figma 근거(경고색·뱃지 비교) 확인했고
>   저희 판단(원시값 비례)과 정확히 일치합니다. 이 항목은 양쪽 다 더 할 일이
>   없어 **닫힘으로 내립니다.**
>
> 아직 답변이 없는 건 **11 · 12 · 15**와 **25(세분화) · 27**입니다. 결국 진짜
> 병목은 **문장 생성 규칙**(B-5, 11·27·25 문구 부분을 같이 막고 있음) 하나로
> 좁혀졌습니다. 14·24 는 여전히 일부만 풀려 있고, 7·19 는 기획 결정 대기입니다.

> **백엔드 5차 회신 (2026-08-17) — 배포 완료**: 남아있던 것 중 두 개를 더
> 결정·배포했습니다.
>
> - **7번 `stressLevel` 0 허용·배포**: 0을 허용하는 쪽으로 정했습니다. 슬라이더를
>   그대로 0~10으로 두시고 값을 그대로 보내시면 됩니다(생략 시 결측 처리는 기존과
>   동일). 채점식 분모도 9→10으로 다시 맞췄습니다(`s = 100 × (10 − x) / 10`,
>   도메인 `[0,10]`) — 기존 1~10 점수도 새 공식으로 다시 계산되어 화면에 소급
>   반영됩니다. 참고로만 알려드리면, 내부 워크드 예시 문서(§B-3)의 참고값 하나가
>   이 조정으로 소폭 이동했는데(정신 영역 66.98→66.17) 이건 저희 내부 문서
>   숫자일 뿐 API 응답이나 서비스 동작에는 영향이 없습니다.
> - **25번 오브 7색 enum·배포**: `GET /api/scores/*` 응답에 `orbState` 필드가
>   추가됐습니다. 값은 7종 — `DANGER_LOW`(0~19) · `DANGER_HIGH`(20~39) ·
>   `WARN_LOW`(40~54) · `WARN_HIGH`(55~69) · `GOOD_LOW`(70~79) · `GOOD_MID`(80~89) ·
>   `GOOD_HIGH`(90~100). 22번에서 이미 배포된 3단계(`grade`) 경계값(70/40) 위에서
>   각 구간을 다시 3등분한 하드 경계라, `orbState` 와 `grade` 가 절대 어긋나지
>   않습니다(예: `orbState` 가 `GOOD_*` 면 `grade` 는 항상 `GOOD`). 색 자체를
>   무엇으로 매핑할지는 프론트에서 정해주시면 됩니다. **상태 칩·설명 문장은
>   여전히 27번(문장 생성 정책)에 막혀 있어 이번 배포 범위가 아닙니다.**
>
> 이걸로 **11 · 12 · 15**, **25(문구만)** · **27**, 그리고 **19번(닉네임만)** 이
> 남았습니다.

**검토 범위는 Figma 전체입니다.** 아직 안 만든 화면도 디자인 기준으로 대조했기
때문에, 이 문서는 "만든 것" 목록이 아니라 **디자인 전체에 대한 요청 목록**입니다.

## 🔴 열림 — 백엔드 답변 대기

### 10. 홈 상단 지표 카드 3개

**🟡 프론트** · 다음: 프론트 (막고 있던 것 둘 다 풀림)

홈에 **수면 6.4시간 / 수분 1.6L / 스트레스 72%** 카드가 있고, 각각
조금 부족·좋아요·높음 같은 등급 뱃지가 붙습니다.

그런데 일지는 값을 **구간(enum)으로만** 저장합니다. `waterIntake`는 "3~5잔"이지
1.6L이 아니고, `stressLevel`은 1~10이지 72%가 아닙니다.

**요청**: 이 세 숫자와 등급을 내려주는 엔드포인트가 필요합니다. 프론트가 enum을
임의로 리터·퍼센트로 환산하면 백엔드 점수 로직과 어긋납니다.

일지의 **일간 컨디션 요약** 카드도 같은 문제입니다 — `수면 7.1h`(이건
`sleepMinutes`로 가능) 옆에 **`수분 3컵`**, `스트레스 6/10`, `기분 좋음`이 함께

### 7. `stressLevel` 최솟값이 1인데 슬라이더는 0부터

**🟡 프론트** · 다음: 프론트 (배포 완료)

`DiaryRequest.stressLevel`은 `1..10`인데 일지 화면 슬라이더는 **0~10**입니다.
0을 보내면 검증 실패합니다.

**요청**: 0을 허용해주시거나, 슬라이더를 1~10으로 바꿔야 한다고 알려주세요.

> 참고: 프론트에는 별도로 "슬라이더가 0과 미응답을 구분 못 한다"는 미해결 이슈가
> 있습니다. `stressLevel`이 optional이니 **미응답이면 필드를 아예 안 보내는** 것으로
> 처리하려고 합니다. 이 해석이 맞는지 확인 부탁드립니다.

> **백엔드 메모 (2026-08-16)**: 아직 결정 못 했습니다 — 단순 검증 문제가 아니라
> 채점식과 얽혀 있습니다. 현재 점수식(`s = 100 × (10 − x) / 9`)의 분모 9는 도메인
> `[1,10]`에 맞춘 값이라, 0을 그냥 허용하면 0과 1이 둘 다 만점으로 나와 버려서
> 11단계를 쓰는 의미가 없어집니다. 0을 정말 넣으려면 분모를 10으로 바꿔야 하는데
> 그러면 1~10의 기존 점수도 전부 바뀝니다(재보정 필요). 내부 문서
> (`docs/PLANNING_OPEN_ITEMS.md` A-6)에 옵션 두 개를 올려뒀고 기획 확인 후
> 회신하겠습니다. **미응답 시 필드 생략** 해석은 맞습니다 — 그대로 쓰시면 됩니다.

> **백엔드 메모 2 (2026-08-17, 배포 완료)**: 0을 허용하는 쪽으로 정했습니다.
> 슬라이더를 그대로 0~10으로 두시고 값을 그대로 보내시면 됩니다(생략 시 결측

> (`s = 100 × (10 − x) / 10`, 도메인 `[0,10]`) — 기존 1~10 점수도 새 공식으로

### 26. 지표 단위가 화면과 API에서 다름

**✅ 닫힘** · 반영 2026-08-17

같은 지표를 화면과 API가 다른 단위로 다룹니다. 프론트가 임의로 환산하면 서버 값과
어긋나기 때문에 손대지 않고 있습니다.

| 지표 | 화면 | API |
|---|---|---|
| 수분 | 홈 `1.6L`, 일간 요약 `3컵` | `waterIntake` = `UNDER_2`/`THREE_TO_FIVE`/`SIX_TO_SEVEN`/`EIGHT_OR_MORE` (컵 **구간**) |
| 스트레스 | 홈 `72%` | `stressLevel` = 1~10 정수 |
| 수면 | 홈 `6.4시간`, 일간 요약 `7.1h` | `sleepMinutes` (분) — 이건 환산 가능 |

수분은 **화면끼리도 단위가 다릅니다**(리터 vs 컵). 구간 enum에서는 어느 쪽도
나오지 않습니다.

**요청**: 두 가지 중 하나로 정해주세요 — (A) 화면 표기를 API에 맞춰 구간 문구로
바꾼다(디자인 변경), (B) 서버가 표시용 값을 같이 내려준다. 스트레스 `%`도
`stressLevel`에서 어떤 식으로 환산하는지가 정해져야 합니다.

> **백엔드 메모 (2026-08-17)**: **수분은 (A)로 결정합니다** — 화면을 API 구간
> 문구(`3~5잔` 등)에 맞춰주세요. 이유: "컵 1개 = 몇 mL"라는 환산 계수는 저희
> 데이터 어디에도 근거가 없습니다. 지어낸 계수로 리터 값을 만들면 이 프로젝트가
> 처음부터 지켜온 원칙("근거 없는 anchor 값을 지어내지 않는다" — `docs/PLANNING_OPEN_ITEMS.md`
> A-3/A-4 등에서 이미 반복 적용됨)을 어기는 겁니다. 화면끼리 단위가 다른 것(리터
> vs 컵)도 이 결정으로 자연히 같은 구간 문구로 통일됩니다.
>
> **스트레스는 아직 결정 못 했습니다** — 수분과 성격이 다릅니다. 여기는 지어낼
> 계수가 필요한 게 아니라, 이미 **두 가지 서로 다른 정당한 해석**이 코드에
> 공존합니다: (1) `stressLevel` 원시값을 그대로 선형 환산 `(x−1)/9×100` — 값이
> 클수록 스트레스가 "높다"는 직관적 읽기, (2) 이미 구현된 채점 공식
> `ItemScores.stress() = 100×(10−x)/9` — 이건 "웰빙 방향"이라 값이 클수록
> 스트레스 관리가 "잘 되고 있다"는 뜻으로 방향이 반대입니다. 화면의 `72%`가
> 어느 쪽을 의도한 건지는 저희가 코드만 보고 판단할 수 없어서(둘 다 나름의
> 근거가 있는 해석입니다), Figma 쪽에 "72%가 스트레스가 높다는 뜻인지 낮다는
> 뜻인지"만 확인해주시면 그 자리에서 결정하겠습니다.

> **프론트 회신 (2026-08-17)**: 확인했습니다.
>
> **수분은 반영 완료**입니다 — 홈의 `1.6L`과 일간 요약의 `3컵`을 둘 다
> `3~5잔`으로 바꿨습니다. `journal-options.ts`의 `WATER`가 이미 API 구간과
> 같은 문구라 표기가 앱 전체에서 일치합니다. 근거 없는 환산 계수를 만들지
> 않는다는 판단에 동의합니다.
>
> **스트레스 `72%`는 "높다"는 뜻입니다 — 해석 (1)이 맞습니다.** Figma에서
> 확인한 근거:
>
> - 같은 카드의 뱃지가 **`높음`**이고, 색이 `#D25D53` 글자 / `#F9E9E8` 배경 —
>   경고색입니다 (`188:1017`, `188:1018`).
> - 같은 줄의 수분 카드는 `좋아요` + 초록 `#4B9977`, 수면은 `조금 부족` +
>   주황 `#E5A64E`. 즉 뱃지 색이 좋음/경고를 구분하는데, 스트레스만 빨강입니다.
> - 웰빙 방향(해석 2)이라면 72%는 "관리가 잘 되는 중"이라 초록 `좋아요`가
>   나와야 하는데 그렇지 않습니다.
>
> 그러니 화면의 `%`는 `stressLevel` 원시값을 그대로 선형 환산한
> `(x−1)/9×100`입니다. 다만 **채점 공식(`ItemScores.stress()`)은 웰빙 방향
> 그대로 두시는 게 맞다고 봅니다** — 그건 점수 계산용이고, 이 카드는 지표를
> 날것으로 보여주는 자리라 방향이 서로 달라도 모순이 아닙니다. 두 값이 한
> 화면에 같이 나오는 곳은 없습니다.

> **백엔드 메모 (2026-08-17, 닫힘)**: 저희도 같은 결론(원시값 비례)으로
> 독립적으로 판단했었는데, 보내주신 Figma 근거로 확실히 확인됐습니다.
> 채점 공식은 그대로 두는 것에도 동의합니다 — 이유가 같습니다(지표 원본
> 표시 vs 웰빙 방향 점수는 쓰임이 달라서 방향이 달라도 됨). 수분·스트레스
> 둘 다 결론 났고 코드 변경도 필요 없어서 이 항목은 닫습니다.

### 1. `SignUpRequest.agreements`의 형태

**✅ 닫힘** · 다음: —

- `SignUpRequest.agreements: Map<AgreementType, Boolean>`. JSON 키는 enum
  상수명 그대로 4개입니다: `TERMS_OF_SERVICE`, `PRIVACY_SENSITIVE`, `MARKETING`,

- 값은 `boolean`만 보내면 됩니다 — `agreedAt`은 서버가 저장 시점에 직접 찍으므로
  요청에 넣을 필요 없습니다.
- `MARKETING`은 이미 서버에서 필수로 검증하지 않습니다(동의 안 해도 가입됩니다).

- 예시:
  ```json
  {"TERMS_OF_SERVICE": true, "PRIVACY_SENSITIVE": true, "MARKETING": false, "AGE_OVER_14": true}
  ```

### 2. 로그인 식별자를 아이디로 변경

### 3. 인증이 필요한 엔드포인트가 어디인지

**✅ 닫힘** · 다음: —

- 인증 없이 열리는 곳: `GET /health`, `POST /api/auth/signup`,
  `POST /api/auth/login`, 문서 엔드포인트(`/v3/api-docs/**`, `/swagger-ui/**`).
- 그 외 전부(`GET /api/auth/me`, `GET /api/dna`, `/api/diaries/**`,
  `/api/scores/**`)는 `Authorization: Bearer <JWT>`가 필요합니다.
- 각 오퍼레이션에 `security` 선언이 이미 있어 `/v3/api-docs`에서 오퍼레이션별로도
  확인 가능합니다.

### 4. 에러 응답 규격

**✅ 닫힘** · 다음: —

- RFC 9457 `application/problem+json`으로 통일돼 있습니다. 공통 필드: `type`,
  `title`, `status`, `detail`, `instance`. 검증 실패에는 `errors: { "필드명":
  "메시지" }`가 추가로 붙습니다.
- 상태 코드:
  - 로그인 실패(아이디 없음/비밀번호 틀림 — 구분해서 알려주지 않습니다) → **401**
  - 아이디 중복 가입 → **409** (`title: "아이디 중복"`)
  - 이메일 중복 가입 → **409** (`title: "이메일 중복"`)
  - 요청 값 검증 실패(필드별 `errors` 포함) → **400**
  - 가입 조건 미충족(만 14세 미만 등) → **400**
  - 일지/초기 진단 없음 → **404**

### 5. `sleepStartedAt` / `sleepEndedAt` 포맷

**✅ 닫힘** · 다음: —

- `"HH:mm"` 또는 `"HH:mm:ss"`(날짜 없는 시각). 예: `"23:30"`.
- 자정 넘김은 서버가 자동 처리합니다 — 기상 시각이 취침 시각보다 이르거나 같으면
  자정을 넘긴 것으로 보고 계산합니다. 별도 플래그나 날짜 필드는 필요 없습니다.
- 응답의 `sleepMinutes`는 말씀하신 대로 서버가 계산해서 내려줍니다.

### 6. 민감도 3종: 0~10 슬라이더 vs 4단계 enum

**✅ 닫힘** · 다음: —

- 4단계 enum(`NONE`/`SLIGHT`/`MODERATE`/`HIGH`)이 맞습니다. 기획이 이미 "슬라이더
  제거, 4점 척도로 통일"로 확정한 사안이라 목업의 0~10 슬라이더 쪽이 구버전입니다.
  화면을 4지선다(전혀 아님/약간/보통/매우)로 바꿔주세요.

### 20. 만 14세 확인을 누가 하나 — `birthYear`에 상한이 없음

**✅ 닫힘** · 다음: —

### 23. 기록이 없는 날은 어떻게 응답하나

**✅ 닫힘** · 다음: —

  맞습니다.
