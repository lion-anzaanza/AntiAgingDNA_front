# 백엔드 요청 백로그

프론트에서 백엔드에 확인·요청할 것들을 모아두는 문서입니다. **이 문서는 계속
관리합니다** — 새로 발견하면 추가하고, 해결되면 아래 "해결됨"으로 내리고 날짜를
적습니다.

- API 레퍼런스: [backend-api.md](backend-api.md)
- Swagger: <https://antiaging-dna.anzaanza.cloud/swagger-ui/index.html>
- 기준 스펙: `GET /v3/api-docs` (OpenAPI 3.1.0, `info.version` = `v0`)
- 최초 작성: 2026-08-16 · 아래 항목들은 이 날짜의 스펙 기준입니다

**검토 범위: Figma 전체 섹션입니다.** 구현된 화면(로그인·회원가입 3단계·홈·
일지/오늘의기록)뿐 아니라 **아직 안 만든 화면도 디자인 기준으로 전부 대조**했습니다
— 일지 나머지 3개(메인·캘린더·상세보기), 05_개선책 4개, 06_마이페이지 4개. 즉 이
문서는 "지금까지 만든 것" 목록이 아니라 **디자인 전체에 대한 요청 목록**입니다.

우선순위는 **프론트가 막히는 정도** 기준입니다. P1은 이게 없으면 화면을 못 붙입니다.

## P1 — 이게 정해져야 연동을 시작할 수 있음

### 1. `SignUpRequest.agreements`의 형태

스펙에 `object`로만 되어 있고 속성이 하나도 없습니다. 프론트 약관 화면은 현재 4개를
받습니다.

| key | 화면 문구 |
|---|---|
| `service` | [필수] 서비스 이용약관 |
| `sensitive` | [필수] 개인정보 민감정보 처리 동의 |
| `marketing` | [필수] 마케팅 정보 수신 |
| `age` | [필수] 만 14세 이상입니다 |

**요청**: 정확한 키 이름과 타입을 알려주세요. `{ "service": true, ... }` 형태면
되는지, 아니면 동의 시각(`agreedAt`)도 같이 보내야 하는지요.

> 참고: 마케팅 수신이 `[필수]`인 것은 별도 이슈입니다. 정보통신망법상 광고성 정보
> 수신 동의는 선택이어야 하고 가입을 막으면 안 됩니다. 디자인 쪽에도 올려둔
> 사안이라 백엔드에서도 필수로 검증하지 않도록 확인이 필요합니다.

### 2. 로그인 식별자를 아이디로 변경 ✅결정됨 → 서버 변경 필요

**결정 (2026-08-16, 기획):** 로그인은 **아이디**로 합니다. 이메일 로그인은 폐기된
옛 안입니다. 디자인의 로그인 화면("아이디를 입력하세요")이 맞습니다.

현재 스펙은 아직 이메일 기준입니다.

**요청**:
- `LoginRequest.email` → 아이디 필드로 교체 (필드명은 서버 편한 대로,
  `loginId` / `username` 등 정해서 알려주세요)
- `SignUpRequest`에도 같은 필드 추가 — 지금은 아이디를 만들 방법이 없습니다
- 아이디 규칙을 알려주세요: 허용 문자, 길이, 대소문자 구분 여부, 중복 검사 여부
- `email`을 계속 필수로 받을지도 함께 정해주세요 (아래 18번과 이어집니다)

### 3. 인증이 필요한 엔드포인트가 어디인지

`bearerAuth`(JWT)가 `securitySchemes`에 정의돼 있는데 **어떤 오퍼레이션에도
`security`가 선언돼 있지 않습니다.** 지금은 "`/api/auth/signup`, `/api/auth/login`
빼고 전부 필요하겠지" 라고 추측만 하고 있는 상태입니다.

**요청**: 각 엔드포인트에 `security` 선언을 넣어주시거나, 최소한 목록으로 알려주세요.

### 4. 에러 응답 규격

성공 응답(200/201/204)만 문서화돼 있습니다. 400·401·409·500이 어떤 바디로
오는지 알 수 없어서 에러 처리를 설계할 수 없습니다.

**요청**: 공통 에러 스키마(예: `{ code, message, fieldErrors }`)와 주요 상황별
상태 코드를 정해주세요. 특히 필요한 것:

- 로그인 실패 (401? 400?)
- 아이디 중복 가입 (409?)
- 검증 실패 시 어떤 필드가 틀렸는지 내려오는지

> 프론트 쪽 사정도 같이 적어둡니다. **지금은 오류를 보여줄 자리가 없습니다** —
> 디자인에 입력 필드의 에러 상태가 없고(`TextInput`은 입력 전/후/비밀번호 세
> 변형뿐), 로그인 화면에도 실패 메시지를 놓을 공간이 없습니다. 필드 단위 오류를
> 내려주셔도 당장은 표시할 수 없어서, 디자인 쪽에 에러 상태를 요청해둔 상태입니다.
> 규격만 정해주시면 프론트에서 맞춰 붙이겠습니다.

### 5. `sleepStartedAt` / `sleepEndedAt` 포맷

타입이 `string`인데 `format`이 없습니다. `"23:30"`인지 `"2026-08-16T23:30:00"`인지,
자정을 넘긴 취침을 어떻게 표현하는지 알 수 없습니다.

**요청**: 포맷을 확정해주세요. 취침이 전날이고 기상이 당일인 경우(대부분)를 어떻게
다루는지도 함께요. 응답의 `sleepMinutes`는 서버가 계산해주는 것으로 이해했습니다.

### 18. 가입 화면에 아이디 입력란이 없음

2번이 확정되면서 드러난 구멍입니다. 회원가입 STEP 1이 받는 항목은
**닉네임 · 이메일 · 비밀번호 · 비밀번호 재확인**뿐이고, **아이디를 받는 칸이
없습니다.** 로그인은 아이디를 요구하는데 가입 과정에서 아이디가 만들어지지 않습니다.

가능한 정리 방향(기획·디자인 확인 필요):

| 안 | 내용 | 영향 |
|---|---|---|
| A | 이메일 칸을 **아이디로 교체** | 이메일을 아예 안 받게 됨 → 비밀번호 찾기 수단이 사라짐 |
| B | 아이디 칸을 **추가** (이메일 유지) | STEP 1 입력이 5개로 늘어남 |
| C | **닉네임을 아이디로 사용** | 별도 표시 이름이 없어짐 |

**요청(백엔드)**: 어느 쪽이든 `SignUpRequest` 필드 구성이 바뀝니다. 서버가 선호하는
안이 있으면 알려주세요. 특히 **이메일을 필수로 유지할지** — 비밀번호 찾기(14번)를
이메일로 할 계획이면 B가 사실상 강제됩니다.

> 프론트는 결정 전까지 로그인·가입 폼을 그대로 두겠습니다.

### 19. 아이디·비밀번호·닉네임의 검증 규칙

스펙에 `password`는 그냥 `string`, `nickname`도 `string`이고 길이·문자 제약이
전혀 없습니다. 그런데 **화면에는 이미 규칙이 적혀 있습니다** — 비밀번호 입력란의
placeholder가 `"8자리 이상, 영문 숫자 포함"`입니다.

지금 상태로는 프론트가 클라이언트 검증을 붙일 수 없습니다. 서버 규칙을 모르는 채
자체 규칙을 만들면, 프론트는 통과시켰는데 서버가 거절하는 상황이 생깁니다.

**요청**: 세 가지 규칙을 확정해주세요.

| 항목 | 알려주실 것 |
|---|---|
| 아이디 | 허용 문자, 최소·최대 길이, 대소문자 구분, 예약어 여부 |
| 비밀번호 | 최소 길이, 필수 문자 종류, 최대 길이 |
| 닉네임 | 최소·최대 길이, 허용 문자, **중복 허용 여부** |

가능하면 스펙의 `minLength`/`maxLength`/`pattern`에 넣어주시면 프론트가 그대로
따라갈 수 있습니다.

### 22. 점수 → 등급 구간 기준 (여러 화면이 같이 씁니다)

디자인 곳곳이 점수를 **등급으로 바꿔서** 보여주는데, 그 경계를 프론트가 알 수
없습니다. `DailyScoreResponse`는 `dailyTotal`/`displayTotal` 숫자만 줍니다.

같은 기준을 쓰는 것으로 보이는 곳:

| 화면 | 표현 | 단계 |
|---|---|---|
| 일지/캘린더 | 날짜 셀 색 (`Date_Low`/`Mid`/`High`) | 3단계 + 기록없음 |
| 일간 컨디션 요약 | `컨디션 좋음` 뱃지 | ? |
| 일지/메인 지난 기록 | 점수 옆 이모티콘 (`ദ്ദി ˃ ᴗ ˂ )` / `(ง •̀_•́)ง` / `( •́ ̯•̀ )`) | 3단계 |
| 홈 5개 영역 밸런스 | `DNAKind` 좋음/주의/위험 | 3단계 |
| 홈 주간 카드 | `_Word` 좋음/주의/위험 | 3단계 |
| 홈 지표 카드 | 조금 부족 / 좋아요 / 높음 | 3단계 |

**요청**: 경계값을 정해주세요. 프론트가 임의로 자르면 **서버가 계산한 점수와 화면
등급이 어긋납니다.** 가능하면 응답에 등급을 같이 내려주시는 게 가장 안전합니다
(예: `displayTotal` 옆에 `grade: "GOOD" | "WARN" | "DANGER"`). 영역별 점수
(`AreaScoreResponse`)도 같은 등급 체계를 쓰는지 확인 부탁드립니다.

### 23. 기록이 없는 날은 어떻게 응답하나

일지/캘린더는 한 달을 한눈에 보여주면서 **기록이 있는 날과 없는 날을 구분**해야
하고(`Date_None` 상태가 따로 있습니다), 일지/상세보기에도 `응답 완료` / `미응답`
표시가 있습니다.

**요청**: 두 가지만 알려주세요.

- `GET /api/diaries/{date}` — 그날 기록이 없으면 404인가요, 200에 빈 값인가요?
- `GET /api/scores?from&to` / `GET /api/diaries?from&to` — 기록 없는 날도 배열에
  포함되나요, 있는 날만 오나요? 캘린더에서 "안 쓴 날"을 그리려면 이게 중요합니다

> 항목 단위 미응답은 `DiaryRequest`가 `conditionLevel` 빼고 전부 optional이라
> null로 구분하면 되는 것으로 이해했습니다. 맞는지만 확인 부탁드립니다.

## P2 — 값이 안 맞아서 매핑 규칙이 필요함

### 6. 민감도 3종: 0~10 슬라이더 vs 4단계 enum

초기 진단 화면은 당분·카페인·스트레스 민감도를 **0~10 슬라이더**로 받는데,
`DiagnosisRequest`는 `NONE / SLIGHT / MODERATE / HIGH` 4단계입니다.

**요청**: 둘 중 하나로 정해주세요.
- 백엔드가 0~10을 받는다 (`sensitivityCoefficients`가 double인 걸 보면 이쪽이
  자연스러워 보입니다), 또는
- 프론트가 4단계로 구간을 나눈다 → **경계값을 알려주세요** (예: 0~2 NONE,
  3~5 SLIGHT, 6~8 MODERATE, 9~10 HIGH). 프론트가 임의로 정하면 점수가 틀어집니다.

### 7. `stressLevel` 최솟값이 1인데 슬라이더는 0부터

`DiaryRequest.stressLevel`은 `1..10`인데 일지 화면 슬라이더는 **0~10**입니다.
0을 보내면 검증 실패합니다.

**요청**: 0을 허용해주시거나, 슬라이더를 1~10으로 바꿔야 한다고 알려주세요.

> 참고: 프론트에는 별도로 "슬라이더가 0과 미응답을 구분 못 한다"는 미해결 이슈가
> 있습니다. `stressLevel`이 optional이니 **미응답이면 필드를 아예 안 보내는** 것으로
> 처리하려고 합니다. 이 해석이 맞는지 확인 부탁드립니다.

### 8. `exerciseType`의 네 번째 값이 서로 다름

- API: `WALKING` `AEROBIC` `STRENGTH` `STRENGTH_AND_AEROBIC`
- 디자인: 걷기 · 유산소 · 근력 · **기타**

"근력+유산소"와 "기타"는 다른 의미입니다.

**요청**: 어느 쪽이 맞나요? 디자인이 맞다면 `OTHER`가 필요하고, API가 맞다면 디자인
문구를 바꿔야 합니다.

### 9. `walkDuration` 두 번째 값의 문구 차이

- API: `UNDER_30` / `THIRTY_TO_60` / `ONE_TO_TWO_HOURS` / `OVER_2_HOURS`
- 디자인: 30분 이하 / **1시간** / 2시간 / 2시간 이상

구간 자체는 대응되는데 라벨이 "1시간"이라 사용자에게는 "정확히 1시간"으로 읽힙니다.
큰 문제는 아니지만 디자인 쪽 문구를 "30분~1시간"으로 맞추는 게 나을지 의견 주세요.

### 20. 만 14세 확인을 누가 하나 — `birthYear`에 상한이 없음

`birthYear`는 `minimum: 1900`만 있고 **상한이 없습니다.** 2030을 보내도 통과합니다.

그런데 약관 화면에는 `[필수] 만 14세 이상입니다` 체크박스가 따로 있습니다. 즉
**나이를 생년으로도 받고 자기신고로도 받는** 구조입니다.

**요청**: 서버가 `birthYear`로 만 14세를 검증하나요? 검증한다면 체크박스는 사실상
의미가 없고, 검증하지 않는다면 상한(예: 올해 − 14)을 넣어주셨으면 합니다. 둘 중
어느 쪽인지에 따라 프론트 검증도 달라집니다.

### 21. 가입 직후 바로 로그인 상태인지 (이메일/본인 인증 유무)

`POST /api/auth/signup`이 201과 함께 `TokenResponse`를 바로 내려줍니다. 이대로면
**가입하자마자 인증된 상태**가 되고, 별도의 이메일 인증이나 본인확인 절차가 없습니다.

디자인도 약관 동의 후 곧바로 홈으로 넘어가는 흐름이라 지금은 일치합니다.

**요청**: 이 설계가 확정인지 확인만 부탁드립니다. 나중에 이메일 인증을 넣을 계획이면
가입 직후 화면 흐름이 바뀌므로 미리 알려주세요.

## P3 — 디자인에 있는데 API에 없음

### 10. 홈 상단 지표 카드 3개

홈에 **수면 6.4시간 / 수분 1.6L / 스트레스 72%** 카드가 있고, 각각
조금 부족·좋아요·높음 같은 등급 뱃지가 붙습니다.

그런데 일지는 값을 **구간(enum)으로만** 저장합니다. `waterIntake`는 "3~5잔"이지
1.6L이 아니고, `stressLevel`은 1~10이지 72%가 아닙니다.

**요청**: 이 세 숫자와 등급을 내려주는 엔드포인트가 필요합니다. 프론트가 enum을
임의로 리터·퍼센트로 환산하면 백엔드 점수 로직과 어긋납니다.

일지의 **일간 컨디션 요약** 카드도 같은 문제입니다 — `수면 7.1h`(이건
`sleepMinutes`로 가능) 옆에 **`수분 3컵`**, `스트레스 6/10`, `기분 좋음`이 함께
나옵니다. "3컵"은 `waterIntake`의 `THREE_TO_FIVE` 구간에서 나올 수 없는 숫자입니다.
같은 엔드포인트로 묶어주셔도 좋습니다.

### 11. 나의 LifeDNA 정보 — 주간 추이 카드

홈의 "수면 시간", "수분 섭취량" 카드는 **7일치 막대 그래프 + 진행 바 +
좋음/주의/위험 라벨 + 코멘트 문장**("올빼미형 - 취침이 3일째 30분씩 빨라졌어요")로
구성돼 있습니다.

`GET /api/dna`는 진단 스냅샷과 baseline만 주고 추이 데이터가 없습니다.

**요청**: 지표별 주간 추이 엔드포인트가 필요합니다. 특히 **코멘트 문장을 서버가
생성하는지** 확인 부탁드립니다 — 프론트에서 만들 성격의 문구가 아닌 것 같습니다.

같은 성격의 문장이 여러 곳에 있습니다. 한 번에 정해주시면 좋겠습니다.

| 화면 | 문장 |
|---|---|
| 홈 주간 카드 | `올빼미형 - 취침이 3일째 30분씩 빨라졌어요.` |
| 일간 컨디션 요약 | `전반적으로 안정적입니다. 스트레스 관리가 조금 더…` |
| 주간 컨디션 그래프 | `어제보다 수면 +40분 · 스트레스 −1` |
| 주간 리포트 | `수면 리듬과 스트레스 회복이 좋아지고 사회 교류는 조금 줄었어요.` |
| 개선책 인사이트 | `수면 7시간 → 컨디션 +6점`, `당분 3회 → 컨디션 -8점` |

`어제보다 …` 류는 점수 두 날치로 프론트가 만들 수 있지만, 나머지는 규칙이 서버에
있어야 할 문장으로 보입니다.

### 12. 날씨 자동 기록

응답에 어떤 필드로 오는지 알려주세요.

### 13. 회원가입에서 받지만 보낼 곳이 없는 항목

STEP 1에서 받는데 `SignUpRequest`에 자리가 없습니다.

**요청**: 성별·직업을 받을 계획이 있나요? 없으면 프론트에서 입력을 빼겠습니다
(안 쓰는 걸 받는 건 개인정보 최소수집 원칙에도 어긋납니다).
생년월일도 연도만 쓸 거면 화면을 연도 입력으로 바꾸는 게 맞습니다.

### 14. 인증 부가 기능

전부 없습니다.

- **토큰 갱신** — `TokenResponse`에 `expiresIn`은 있는데 refresh token이 없습니다.
  만료되면 재로그인만 가능한 구조인지, refresh를 넣을 계획인지 알려주세요
- **로그아웃** — 서버 세션/토큰 무효화가 필요한지
- **아이디·비밀번호 찾기** — 로그인 화면에 링크가 있습니다
- **이메일 중복 확인** — 가입 폼에서 미리 확인할 수 있으면 UX가 낫습니다

### 15. 05_개선책 — 화면 4개, 엔드포인트 0개

하단 탭에 자리는 있지만 비활성 상태입니다. 디자인상 필요한 것:

**개선책/메인** — `오늘의 실천` 체크리스트가 핵심입니다.
- 오늘의 실천 항목 목록 (예: `오전에 물 2잔 이상 마시기`, `취침 1시간 전 스마트폰
  내려놓기`, `햇빛 15분 쬐기`). Figma 메모를 보면 **5영역(신체·정신·감정·사회·환경)
  별로 분류된 항목 풀에서 그날 부족한 영역에 맞춰 노출**하는 설계입니다
- 항목별 완료 처리 (`완료!` 버튼) → **완료 상태를 저장하는 엔드포인트 필요**
- 실천율 `70%` 진행바

**개선책/맞춤영양제** — **커머스가 들어옵니다.**
- 추천 영양제 목록: 제품명(`마그네슘 · 테아닌`), 근거 태그(`스트레스 누적형 ·
  수면 질 ↓`), 근거 문장, **가격(`월 12,900원 / 30일분`)**
- `담기` 버튼, `3종 정기구독으로 담기` → **장바구니·구독·결제 도메인 전체**
- 추천 근거가 `'올빼미 - 고민감 - 누적형'과 최근 일지를 바탕으로` 라고 적혀 있어
  서버 추천 로직이 전제됩니다

**개선책/주간리포트**
- `이번 주 평균 79점 ▲3`, 지난 주 대비 **영역별 증감**(신체 +5, 감정 +2, 환경 −3…)
- `이번 주 인사이트` / `다음 주 제안` 카드 — 문장이 서버 생성인지 확인 필요

**개선책/한달뒤내모습**
- 30일 예상 성장 곡선(`74점 → 81점`), `최근 실천율 78% 유지기준 +7점`
- 시나리오 2개(`지금처럼` 81점 / `조금 더 열심히` 88점)
- **시뮬레이션 계산을 서버가 하는지 프론트가 하는지**가 갈림길입니다

**요청**: 이 섹션은 규모가 커서 일정 공유만이라도 부탁드립니다. 특히 **커머스를
자체 구현할지 외부 결제를 붙일지**는 미리 알아야 프론트 구조가 정해집니다.

### 24. 06_마이페이지 — 화면 4개, 엔드포인트는 `/api/auth/me` 하나뿐

- **프로필 카드** — 닉네임, `연속 기록 82일째`(스트릭), `올빼미 - 고민감 - 누적형`

- **웨어러블 연동** — 애플워치. 연동 플로우·토큰·데이터 수신 전부 미정

**요청**: 최소한 **회원탈퇴**는 다른 항목과 무관하게 먼저 필요합니다.
