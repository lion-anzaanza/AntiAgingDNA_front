# 백엔드 요청 백로그 작성 (lifeDNA)

이 스킬은 **백엔드에게 넘기는 요청 문서를 쓰고 관리하는 단계**를 다룬다. 서버를 화면에 붙이는 작업은 `backend-wire`를 본다.

## 문서 세 개의 역할

한 사실은 한 곳에만 둔다. 어디에 쓸지 헷갈리면 이 표로 정한다.

| 문서 | 읽는 사람 | 담는 것 |
|---|---|---|
| `docs/backend-backlog.md` | 백엔드 | **열린 요청**과 닫힌 번호의 한 줄 목록 |
| `docs/frontend-status.md` | 프론트 | 🟡 우리가 붙일 것, 🟣 기획 대기, 화면별 커버리지 |
| `docs/backend-api.md` | 프론트 | API가 **지금** 어떻게 동작하는지 (확정된 사실) |

- 백로그에 회신 경과나 역사를 쌓지 않는다. 2026-09-30 이전 판은 회신 인용이 문서의 절반(1428줄 중 653줄)이었고, 한 항목의 상태가 세 곳에 따로 적혀 서로 어긋났다.
- 확정된 결정은 백로그가 아니라 `backend-api.md`에 **사실**로 적는다.

## 운영 방식 — 일방 전달

- 프론트가 문서를 넘기고, 백엔드는 **구두로** 답한다. 백엔드는 이 파일을 편집하지 않는다.
- 백엔드가 먼저 만들어 따로 알려준 것은 백로그를 거치지 않는다. 서버에서 확인한 뒤 `backend-api.md`에 적는다. 화면 작업이 생기면 `frontend-status.md`에 새 번호로 연다.

## 쓰기 원칙

백엔드가 읽는 문서다. 사람이 훑어서 **다음에 뭘 해야 하는지** 바로 알아야 한다.

### 개조식

- **명사형으로 끝낸다** — `~함`, `~임`, `~없음`, 또는 명사. `~합니다`, `~입니다`는 쓰지 않는다.
- **서술식과 섞지 않는다.** 한 문서 안에서 문체를 통일한다.
- **한 불릿에는 한 가지 사실.** 두 사실을 마침표나 쉼표로 이어 붙이지 않는다 — 하위 불릿으로 나눈다.
- 표 칸처럼 불릿을 쓸 수 없는 곳에서만 두 사실을 잇는다. 병렬은 ` · `, 인과는 `→`, 대비는 `vs`, 부연은 ` — `.
- **마침표를 찍지 않는다.** 줄 끝에도, 줄 중간에도. 명사형으로 끝나는 문장은 문장 부호 규정상 생략이 허용된다.
- 계층은 최대 3단. 더 깊어지면 항목을 쪼갠다.

### 두괄식

- 문서 전체: **머리 → 열린 요청 표 → 항목 → 닫힘 표 → 작성 규칙** 순서. 머리는 목적 · 최종 갱신일 · 관련 문서만 담은 짧은 불릿 목록이다.
- 항목 안: **요청이 첫 줄**, 배경은 그 뒤. 배경부터 쓰면 무엇을 해 달라는지 끝까지 읽어야 알 수 있다.
- 표의 요청 이름과 항목 제목은 같은 말로 쓴다. 표에서 찾은 제목으로 항목을 바로 찾을 수 있게 한다.

### 정보는 상대의 행동을 바꾸는 것만

- 백엔드의 판단이나 구현을 바꾸지 않는 정보는 넣지 않는다. 프론트 내부 사정은 `프론트 우회` 한 줄로 충분하다.
- 근거가 필요하면 **재현한 호출과 결과**를 적는다. 추측(`~가능성 높음`, `~로 보임`)은 쓰지 않는다.

### 백틱

서버와 주고받는 **값 그 자체**만 백틱으로 적는다. 풀어 쓰거나 번역하지 않는다.

- 백틱: 엔드포인트(`GET /api/scores`), 필드 · enum · 스키마 이름(`dailyGrade`, `GOOD`), HTTP 상태코드(`404`), API가 정한 수치 경계 · 범위(`70` / `40`, `0~10`), 요청 · 응답에 실린 날짜(`2024-06-15`), 계정 · 파일 · 경로
- 백틱 아님: 일반 개수(14일치, 4화면), 회신 줄 앞의 기록 날짜(08-17), 항목 번호(22번), 화면 이름

## 항목 템플릿

```markdown
### {번호}. {무엇이 문제인지 한 줄 — 명사형}

- **요청**: {백엔드가 해 줄 일. 선택지가 있으면 하위 불릿으로}
- **완료 조건**: {프론트가 서버에서 무엇을 확인하면 닫는지}
- **배경**
  - {왜 필요한지 — 어느 화면, 어느 값}
  - {재현한 호출 → 결과}
- **범위 밖**
  - {이 번호에서 이미 끝났거나 다른 문서로 옮긴 하위 요청 → 어디에 있는지}
- **프론트 우회**: {답을 기다리는 동안 프론트가 하는 것}
- **회신**
  - {MM-DD} 구두: {백엔드가 말한 것}
  - {MM-DD} 전달: {프론트가 백엔드에게 말한 것}
  - {MM-DD} 확인: {프론트가 호출한 것 → 결과}
```

- 해당 없는 칸은 지운다. `없음`이라고 채우지 않는다.
- **`완료 조건`은 🔴 항목에 필수**다. 끝을 판정할 수 없는 요청은 닫을 수 없다.
  - "표시 가능"처럼 화면 상태로 쓰지 않는다. 서버에서 확인할 것으로 쓴다 — "응답에 `stressGrade` 존재".
  - ⏸ 보류 항목은 면제한다. 재개해서 🔴로 올릴 때 적는다.
- 규모가 큰 요청(예: 15번)은 `요청 (가장 먼저 필요한 답)`과 `이후 필요한 것`으로 나눈다. 백엔드가 하나를 먼저 정할 수 있게 한다.

## 절차

### 새 요청 추가

1. **서버에서 먼저 확인한다.** `GET /v3/api-docs`와 실제 응답을 보고, API가 정말 못 하는지 확인한다. `backend-wire`의 검증 절차를 따른다(단일 날짜 점수 조회 금지 포함).
2. **번호**: 백로그와 `frontend-status.md`가 공유하는 다음 번호를 쓴다. 번호는 백로그 `작성 규칙`의 "다음 번호"에 있다. 쓴 뒤 두 문서의 "다음 번호"를 모두 1 올린다.
3. 템플릿대로 항목을 쓰고, `열린 요청` 표에 한 줄 추가한다.
4. 백엔드에게 알리는 것은 사람이 한다. 문서를 넘겼다고 알린 것으로 치지 않는다.

### 회신 기록

- 해당 항목 `회신` 목록에 날짜 + **한 줄에 한 사실**. 회신 전문은 옮기지 않는다. 두 사실이면 두 줄로 쓴다.
- 접두어 셋을 섞지 않는다.
  - `구두:` 백엔드가 말한 것
  - `전달:` 프론트가 백엔드에게 말한 것 (반박 · 추가 요청)
  - `확인:` 프론트가 서버를 직접 호출한 것 → 결과. `호출 → 결과`는 한 사실로 친다
- **"배포했다"는 `구두:`다.** 서버를 직접 호출해 확인하기 전까지는 `확인:`이 아니다. 2026-08-17에 "배포 완료" 네 건이 실제 서버에 없었다(배포 스크립트가 실패를 무시).
- `확인:`에는 호출 결과만 적는다. 결과에서 끌어낸 추측은 적지 않는다.
- 회신이 틀렸으면 `확인:`으로 무엇이 나왔는지 적고 🔴로 둔다. 다시 알리는 것은 구두로 하고, 알렸으면 `전달:` 줄을 남긴다.
- 회신 줄은 **말한 그대로** 남긴다. 나중에 그 안의 번호가 닫혀도 고치지 않는다 — 그날 한 말의 기록이다.

### 부분 이관

열린 항목의 일부만 끝났거나 다른 문서로 넘어갈 때(예: 24번의 회원탈퇴 · 유형 라벨).

- 끝난 하위 결정은 `backend-api.md`에 사실로 옮긴다.
- 프론트 · 기획으로 넘어간 부분은 `frontend-status.md`에 **같은 번호로** 연다.
- 항목에 `범위 밖` 칸을 두고, 하위 요청마다 어디로 갔는지 한 줄씩 적는다.
- 항목은 남은 요청이 있는 동안 열어 둔다.

### 닫기

- **`확인:` 없이 닫지 않는다.** 방침만 정한 결정(서버가 바뀌지 않는 것)은 예외다.
- 닫을 때:
  1. 결정을 `backend-api.md`에 사실로 옮긴다.
  2. 항목 본문을 지우고 `닫힘` 표에 한 줄 추가한다.
  3. `열린 요청` 표에서 뺀다.
- **답이 화면 변경을 요구하면 이관한다.** `frontend-status.md`에 같은 번호로 🟡(우리가 할 일) 또는 🟣(기획 대기)를 연다. 이관 없이 닫으면 그 작업이 사라진다 — 네 건이 실제로 그렇게 묻혔다.
- 보류(⏸)는 닫힘이 아니다. 양쪽이 미루기로 합의한 것이라 열린 요청에 남긴다.

### 닫힘 표

| 칸 | 쓰는 것 |
|---|---|
| # | 번호 |
| 닫은 날 | MM-DD (백틱 없이) |
| 결정 | 한 칸 한 결정 — 여러 사실은 ` · ` / `→`로 잇고 마침표 금지 |
| 확인 | 프론트가 서버에서 확인한 날(MM-DD). 서버 변경 없는 결정은 `방침`. 본문을 지워도 확인 여부가 남게 하는 칸 |
| 비고 | `이관 🟡` · `이관 🟣` · `이관 🟡🟣` · `부작용 → {번호}`. 프론트 전용 번호는 `프론트 전용 🟡` |

- 프론트 전용 번호(백엔드와 무관하게 `frontend-status.md`에서 연 번호)도 번호가 비지 않도록 닫힘 표에 한 줄 둔다. 닫은 날 · 확인은 `—`.

## 체크리스트

- [ ] 머리 → 열린 요청 → 항목 → 닫힘 → 작성 규칙 순서인가
- [ ] 표의 요청 이름과 항목 제목이 같은가
- [ ] 요청이 항목 첫 줄에 있는가
- [ ] 🔴 항목에 `완료 조건`이 있고, 서버에서 확인할 수 있는 형태인가
- [ ] 명사형으로 끝나는가, 서술형(`~합니다`)이 섞이지 않았는가
- [ ] 한 불릿에 한 사실인가, 마침표가 없는가
- [ ] 서버 값을 백틱으로 적었는가 (일반 개수 · 기록 날짜는 제외)
- [ ] 회신이 한 줄 한 사실이고 `구두:` / `전달:` / `확인:`을 구분했는가
- [ ] `확인:`에 추측이 섞이지 않았는가
- [ ] 부분 이관한 하위 요청이 `범위 밖`에 적혀 있는가
- [ ] 닫은 항목의 결정을 `backend-api.md`에 옮기고, `확인` 칸을 채웠는가
- [ ] 화면 작업이 남는 답을 `frontend-status.md`로 이관했는가
- [ ] "다음 번호"를 두 문서 모두 갱신했는가
## 이 규칙들의 근거

- 개조식: 명사형 종결, 한 항목 한 내용, 서술식 혼용 금지 — 국내 보고서 작성 관행([개조식 — 나무위키](https://namu.wiki/w/%EA%B0%9C%EC%A1%B0%EC%8B%9D), [보고서 작성시 일반적 유의 사항](https://m.cafe.daum.net/eduparty/d6Fk/34))
- 두괄식: 읽는 사람이 바로 판단하게 핵심을 먼저 둠([패스트캠퍼스 보고서 작성법](https://fastcampus.co.kr/story_article_bsk), [개조식 문서 작성 방법](https://www.eunhah.com/2020/03/234.html))
- 완료 조건: "끝"의 정의가 없는 요청은 판정할 수 없음([Acceptance Criteria — AltexSoft](https://www.altexsoft.com/blog/acceptance-criteria-purposes-formats-and-best-practices/))
- 필요한 칸만: 템플릿은 받는 쪽의 다음 행동을 바꾸는 정보만 요구해야 함([Write Clear Issues with Templates](https://shio-chan-dev.github.io/jeanblog/notes/git-notes/write-clear-issues-from-zero-to-template/))
- 현재 상태와 이력 분리: 현재 상태 문서에 이력을 쌓지 않음([reconcile-rs #120](https://github.com/adriendellagaspera/reconcile-rs/issues/120))
