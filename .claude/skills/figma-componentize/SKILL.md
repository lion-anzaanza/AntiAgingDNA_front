# Figma 컴포넌트화 규칙 (lifeDNA)

이 스킬은 **Figma 파일 자체를 정리하는 단계**(화면의 raw 도형을 `00_디자인_시스템`의 컴포넌트 인스턴스로 교체)에 쓴다. 코드는 한 줄도 안 건드린다. 범용 `figma-use` 스킬(Plugin API 사용법)과 **함께** 로드해서 쓴다.

- Figma 파일: `lifeDNA` (fileKey `dltRYbBH0KHuBe86A6Vr2G`), 페이지 `0:1`

## 디자인 시스템 컴포넌트 카탈로그 (`00_디자인_시스템` > `컴포넌트`, `153:290`)

|---|---|---|

**기본 원칙**: 화면 안의 개별 도형이 위 카탈로그의 컴포넌트와 대응되면(이름 또는 시각적으로), 그 도형을 그대로 두지 말고 해당 컴포넌트의 **인스턴스**로 교체한다. 대응되는 카탈로그 항목이 없는 순수 화면 전용 요소는 그대로 둔다 — 억지로 끼워 맞추지 않는다.

## 선택형 UI(라벨+선택지) 매칭 규칙 — 가장 많이 놓치는 지점

Figma 원본 화면에는 "질문 라벨 + 버튼 여러 개"가 **낱개 도형(사각형+텍스트)으로 흩어져** 있는 경우가 대부분이다. 이걸 볼 때 반드시 두 단계로 확인한다.

1. **먼저 "통짜 컴포넌트"가 있는지 확인한다.** 개별 버튼만 `SelectButtonN` 인스턴스로 바꾸고 끝내지 말 것 — 카탈로그에는 라벨+버튼 묶음 자체가 하나의 컴포넌트로 이미 존재한다. 아래 표로 어떤 선택지 개수·배치가 어떤 컴포넌트에 대응하는지 먼저 매칭한다.
2. 통짜 컴포넌트가 매칭되면, 화면의 개별 라벨 텍스트 + 버튼 도형들을 전부 지우고 그 컴포넌트 인스턴스 **하나**로 교체한다(인스턴스 내부의 `항목명`과 각 버튼의 `버튼명`만 실제 문구로 채움).

| 선택지 개수·배치 | 통짜 컴포넌트 | 내부 pill | pill 크기(기준) |
|---|---|---|---|
| 3개, 한 줄 | `SelectItem3` | `SelectButton2` | 48×17 |
| 4개, 2×2 | `SelectItem4_1` | `SelectButton1_White` | 75×19 |
| 4개, 한 줄 | `SelectItem4_2` | `SelectButton3_White` | 37×16 |
| 5개, 3+2 두 줄 | `SelectItem5` | `SelectButton2_White` | 48×17 |
| 6개, 카드형(배경 박스 있음) | `SelectItem6_Card` | `SelectButton5` | 24×14 |
| 0~10 슬라이더 | `Select0To10` | (바+점+양끝 라벨, 버튼 아님) | 186×43 |

**크기 허용 오차**: 화면의 실제 버튼 폭이 카탈로그 기준값과 ±15% 이내로 차이 나는 건 정상이다(디자인 시스템으로 통일되는 게 원래 목적이므로 억지가 아니다) — 폭이 조금 다르다고 매칭을 포기하지 말 것. 다만 **선택지 개수나 줄 배치 자체가 다르면**(예: 5개가 3+2가 아니라 한 줄로 나열됨, 또는 폭이 2배 이상 들쭉날쭉함) 통짜 컴포넌트를 억지로 쓰지 말고 개별 `SelectButtonN` 인스턴스로만 대응하거나(레이아웃은 화면 것을 유지) 아예 대응 컴포넌트 없음으로 판단한다. 이때는 반드시 왜 안 되는지(개수/배치/폭 차이 수치) 사용자에게 설명할 것 — "대응 없음"이라고 성급히 결론 내리기 전에 표를 다시 훑어보는 습관을 들인다.

**아이콘이 겹쳐 있는 경우**: 원래 raw 도형 위에 아이콘(동물 그림 등)이 얹혀 있던 자리라면, 통짜 컴포넌트 인스턴스를 새로 만들 때 z-order상 아이콘보다 나중에(위에) 생성되어 아이콘을 가릴 수 있다. 아이콘 노드를 `parent.appendChild(iconNode)`로 다시 앞으로 가져와야 한다.

## 네이밍 주의

`버튼` 섹션의 일부 variant 속성명에 오타/혼용이 있다(`SelectButton1` 프레임의 active variant 이름이 `속성 1=SelectButton2_Active`로 되어 있음). 컴포넌트를 찾을 때는 속성명 문자열을 그대로 믿지 말고 실제 프레임 크기·위치로 어떤 SelectButton인지 재확인한다.

## Figma 파일 조작 시 주의사항 (`use_figma`)

- **hidden 프레임에 새 인스턴스를 추가하면 빈 채로 생성된다**: `frame.visible === false`인 프레임에 `createInstance()` 결과를 `appendChild`한 뒤 같은 스크립트에서 바로 `findOne`/`children`을 읽으면 자식이 비어 있어 `null` 에러가 난다. 작업 전 `frame.visible = true`로 잠깐 켰다가, 스크립트 마지막에 원래 hidden이었으면 다시 `false`로 되돌린다.
- **겹쳐진 중복 레이어를 조심한다**: 같은 자리에 완전히 동일한 내용이 두 벌 겹쳐 있는 경우가 실제로 있었다(디자이너의 복붙 실수로 추정). raw 도형을 지우기 전에 같은 텍스트/좌표를 가진 노드가 더 있는지 한 번 더 확인한다.
- **Pretendard 폰트는 Plugin API에서 로드가 안 된다**: 로컬/시스템에 정상 설치되어 있어도 `figma.loadFontAsync({family: 'Pretendard', ...})`는 항상 실패한다(구조적 한계로 확인됨). 텍스트를 새로 채워야 하면 `Noto Sans KR`을 임시로 쓰고, 수정한 텍스트 노드의 `name`에 `[TEMP-FONT: Noto Sans KR -> Pretendard {weight}]`를 붙여 표시한다. 실제 폰트 복원은 사람이 데스크톱 앱에서 직접 해야 한다(레이어 패널에서 "TEMP-FONT" 검색). 코드 쪽은 실제 Pretendard 폰트 파일을 쓰므로 이 제약과 무관하다 — 자세한 건 `figma-implement-component` 스킬 참고.
- **`search_design_system` 툴은 이 파일에서 빈 결과만 준다**: 로컬(비공개) 컴포넌트라 published 라이브러리 검색 대상이 아닌 것으로 보인다. 컴포넌트를 찾을 때는 `get_metadata`/`use_figma`로 `00_디자인_시스템` 섹션을 직접 순회한다.
- **fileKey를 스크립트마다 다시 타이핑하지 말고 복붙할 것**: 한 글자만 틀려도(`86` → `28` 같은) "파일 접근 권한 없음" 에러가 나서 원인 파악에 시간을 뺏긴다.
- **`node.findAll()`이 방금 만든 인스턴스 내부를 못 찾을 때가 있다**: 페이지/서브트리가 완전히 로드되지 않은 상태에서 벌크 탐색하면 일부 노드가 누락될 수 있다. 특정 노드 존재를 검증할 땐 `getNodeByIdAsync`로 직접 조회하거나 `.children`을 직접 재귀하는 게 더 안전하다.

## 작업 절차

1. `get_metadata`로 대상 화면/프레임의 노드 구조를 훑는다.
2. 위 카탈로그·매칭 표로 어떤 raw 도형이 어떤 컴포넌트에 대응하는지 판단한다. 개별 버튼이 아니라 "통짜 컴포넌트"부터 확인한다.
3. `use_figma`로 인스턴스를 만들고 텍스트를 채운 뒤, 대체된 raw 도형을 삭제한다.
4. `get_screenshot`으로 원본과 대조해 깨진 곳(겹침, 잘림, 아이콘 가려짐)이 없는지 확인한다.
5. 대응 컴포넌트가 없다고 판단한 요소는 왜 없는지(개수/배치/폭 차이) 사용자에게 설명한다.

## 체크리스트

- [ ] hidden 프레임 작업 시 visible 토글을 했는가
- [ ] 같은 자리에 중복 레이어가 없는지 확인했는가
- [ ] 텍스트를 채운 노드에 TEMP-FONT 태그를 남겼는가
- [ ] 아이콘이 새 인스턴스에 가려지지 않았는가
- [ ] 스크린샷으로 원본과 대조했는가
